# 10 イレギュラーパターン検証

> 新スコアリング設計が「実装の存在」ではなく「ユーザー体験」を測れているかの検証。
> 各パターンで、旧スコアと新スコアの判定差を見る。

## 検証フォーマット

各パターンは以下で記述:
- **状況**: 実装の実態
- **旧スコア**: 旧 5 軸（機能性30 / 見た目25 / レスポンシブ20 / コード品質15 / a11y10）での判定
- **新スコア**: 新 5 軸 + 落第条件 + 連携ペナルティ での判定
- **差の理由**: なぜ新が正しいか

---

## パターン 1: hero が綺麗だが何屋か分からない

- **状況**: 美しい背景画像、滑らかなパララックス。キャッチコピーは「未来をつくる、私たちの仕事」。業種・地域・対象顧客の情報なし。
- **旧スコア**: 機能性 27/30 + 見た目 25/25 + レスポンシブ 20/20 + コード 13/15 + a11y 8/10 = **93/100 → ✅ PASS**
- **新スコア**:
  - 落第条件: 通過
  - わかる **8/25**（業種不明、対象不明）
  - 信じられる 12/20、欲しいに合う 8/20、動ける 15/20、気持ちいい 14/15
  - 連携ペナルティ 0
  - 合計 **57/100 → ⛔ STOP**（最低保証も 60% 未満で違反）
- **差の理由**: 旧は見た目の良さで合格にしてしまう。新はそもそも「3 秒で何屋か」が伝わらなければ離脱されるという核を測る。

---

## パターン 2: cta-section が header の CTA と重複

- **状況**: ページ下部に「お問い合わせはこちら」CTA を置いたが、header にも常駐 CTA「お問い合わせ」がある。どちらも同じフォームへ。
- **旧スコア**: 機能性 30/30（CTA は存在）+ 見た目 22/25 = **89/100 → ⚠️ CONDITIONAL（軽微な改善で通す）**
- **新スコア**:
  - 落第条件: 通過
  - 5 軸合計 87/100
  - **連携ペナルティ -10**（hero と cta が同一動作で重複）
  - 合計 **77/100 → 🔁 RETRY**
- **差の理由**: 隣との重複は visitor の判断負荷を増やす。旧はその機能単体しか見ないので見逃す。`_adjacency.md` で機械的に検出される。

## パターン 3: 施工実績が PC で綺麗、スマホで縦に長すぎる

- **状況**: PC は 3 カラムで美しい。スマホは 1 カラムで 30 件並び、スクロールしないと全部見えない。
- **旧スコア**: レスポンシブ 20/20（崩れていない）+ 機能性 28/30 + 見た目 24/25 = **91/100 → ✅ PASS**
- **新スコア**:
  - 落第条件: 通過
  - わかる 22/25、信じられる 19/20、欲しいに合う 18/20、動ける 14/20、**気持ちいい 6/15**
  - 連携ペナルティ 0
  - 合計 **79/100 → 🔁 RETRY**
  - **最低保証違反**: 気持ちいいが 40% で 60% 未満
- **差の理由**: 「崩れない」と「気持ちいい」は別物。30 件全部スクロールは visitor を疲れさせる。新はスマホでの体感を測る。

- **差の理由**: 完璧すぎる証拠は逆に信頼を破壊する。旧は「セクションが存在する」で点を入れる。新は「visitor が信じるか」で測る。

- **新スコア**:
  - 落第条件: 通過
  - わかる 20/25、信じられる 16/20、欲しいに合う 14/20、**動ける 10/20**、気持ちいい 14/15
  - 合計 **74/100 → 🔁 RETRY**

  - 落第条件: 通過

## パターン 10: hero 追加で既存 news の更新日が小さくなった

- **状況**: 新しい hero を実装した結果、CSS のグローバル影響で news-section の更新日の文字サイズが 14px → 11px に縮小。視認性が低下。
- **旧スコア**: 新機能（hero）のみ評価し 92/100 で **✅ PASS**
- **新スコア**:
  - hero 単体: 落第通過、5 軸合計 90/100
  - **連携ペナルティ -10**（news-section の劣化を `_adjacency.md` で検出）
  - 合計 **80/100 → 🔁 RETRY**
  - news-section も別途再評価が必要（連鎖検査）
- **差の理由**: 1 機能の追加で他が壊れたら品質ではない。旧は単体しか見ない。新は隣との関係を必ず見る。

## 集計

| 旧判定 | 新判定 | 件数 |
|---|---|---|
| PASS → PASS | 0 | |
| PASS → CONDITIONAL | 0 | |
| PASS → RETRY | パターン 2, 3, 5, 10 | 4 |
| PASS → STOP | パターン 1, 6, 7 | 3 |
| CONDITIONAL → STOP | パターン 4, 8, 9 | 3 |
| 合計 | | 10 |

**観察**:
- 旧スコアでは 10 件中 **7 件が PASS、3 件が CONDITIONAL（軽微改善で通す）**。
- 新スコアでは 10 件中 **0 件が PASS、4 件が RETRY、6 件が STOP**。
- 新は「機能が存在する」を許さず、「core が実現されているか」「隣と協調しているか」で測る。

## このテストを再利用する手順

1. 新しい機能を実装したら、まず上記 10 パターンに該当しないか自己点検
2. 該当する場合、新スコアでの判定に従って対処
3. 新しいイレギュラーを発見したら、本ファイルに追記してパターン 11、12 とする
